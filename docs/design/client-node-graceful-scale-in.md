# Design: graceful scale-in for the client pool

Status: proposed. Nothing in this document is implemented yet.

## Goal

Terminating a client node must not kill running sandboxes. When the Auto Scaling
group decides to remove a client instance, that instance should stop accepting
new sandboxes, keep serving the ones it has until they end on their own, and only
then be terminated.

Non-goals:

- **Scale-out.** No scaling policy is proposed here; the pool still changes size
  only by hand or by an instance refresh. Scale-in correctness has to exist
  before automatic scale-out is safe to add, not the other way round.
- **Pausing sandboxes to drain faster.** Sandboxes are allowed to finish
  naturally (option A in the discussion that produced this document). The
  tier-level cap makes that bounded — see Constraints.
- **The build and api pools.** `template-manager` sets `FORCE_STOP = "true"`
  deliberately (`nomad/origin/template-manager.hcl`), and the api pool holds no
  sandbox state.

## Current state

Verified on the live `e2b-dev` deployment.

### The ASG will terminate instances with no warning

```
client ASG:  min 0, desired 1, max 5
scaling policies:  none
lifecycle hooks:   none
termination policy: Default
scale-in protection: off
health check: EC2, grace 300s
```

No policy means no automatic scale-in today. Termination still happens through
three paths: a manual desired-capacity change, an instance refresh (used twice
already), and EC2 health-check replacement. With `max = 5`, adding any scale-out
policy later immediately creates scale-in events that nothing is prepared for.

### The orchestrator already implements drain

`packages/orchestrator/info.proto` defines the semantics:

> `Draining` means the node is bound to be shut down. It will not accept new
> sandboxes and will stop once all existing sandboxes are done.

`packages/orchestrator/pkg/factories/run.go:1065-1094` implements it on shutdown,
unless `FORCE_STOP` is set — which `orchestrator.hcl` does not set:

1. If the status is `Healthy` or `Standby`, set it to `Draining`.
2. Sleep 15s so the new status reaches every API replica.
3. Wait for the template-manager to drain, if colocated.
4. `DrainSandboxes()` — poll until the live sandbox count is zero
   (`packages/orchestrator/pkg/server/main.go:341`).
5. Close services in reverse order.

The API side is equally ready: `api.NodeStatusDraining` exists,
`Node.CanAcceptNewRequests()` gates placement
(`packages/api/internal/orchestrator/placement/placement_best_of_K.go`), and
`POST /nodes/{nodeID}` changes a node's status under `AdminApiKeyAuth`.

### Three gaps, all in the deployment layer

| # | Gap | Consequence |
|---|---|---|
| 1 | `nomad/origin/orchestrator.hcl` sets no `kill_timeout`, so Nomad's default of **5s** applies | SIGTERM, then SIGKILL 5s later. The drain above cannot even finish its 15s status propagation, so in practice there is no graceful shutdown at all. `run-nomad.sh:244` already sets `max_kill_timeout = "24h"`, so the ceiling is not the problem — the job simply never asks for the budget. |
| 2 | No ASG lifecycle hook | EC2 terminates the instance immediately. Even with gap 1 fixed, nothing waits for the drain. |
| 3 | `admin_token` is regenerated by `infra-iac/terraform/start.sh:191` on every terraform run | Any automation authenticating with it breaks after the next apply. Already broken: the running api job holds one value while `/opt/config.properties` holds another, and `GET /nodes` returns 401. |

## Constraints

- **Sandbox lifetime is capped at 1 hour.** Tier `base_v1` has
  `max_length_hours = 1`, and the API's default `timeout` is 15 seconds. A node's
  drain therefore lasts at most as long as the longest-lived sandbox on it, with
  a one-hour ceiling. If a customer is later given a wider tier, this ceiling
  moves with it — the drain budget below has to be reviewed when that happens.
- **Lambda runs for at most 15 minutes**, so a single invocation cannot hold a
  drain that may last an hour. The wait has to live outside the function.
- **The API identifies nodes by Nomad node UUID**, not by EC2 instance id:
  `orchestrator.hcl:74` sets `NODE_ID = "${node.unique.id}"`. ASG lifecycle
  events carry only the instance id, so something has to bridge the two. Nomad's
  node `Name` is the EC2 instance id, which makes Nomad the bridge (approach M1).
- **The ASG lifecycle hook is the backstop.** With `default_result = CONTINUE`,
  any failure in the automation ends with the instance being released when the
  heartbeat times out, rather than an ASG stuck forever.

## Design

EventBridge starts one Step Functions execution per terminating instance. The
execution marks the node draining, then polls until it is empty, heartbeating the
lifecycle action as it goes, and completes the action when the node is clear.

```
EventBridge rule (event pattern, no schedule)
  source: aws.autoscaling
  detail-type: "EC2 Instance-terminate Lifecycle Action"
  detail.AutoScalingGroupName: e2b-dev-client-asg
        │  one execution per terminating instance
        ▼
┌───────────────────────────────────────────────────────────┐
│ Standard state machine: drain-client-node                 │
│                                                           │
│  MarkDraining        Lambda (in VPC)                      │
│    instance-id → Nomad /v1/nodes where Name == id         │
│    → node UUID → POST /nodes/{uuid} {"status":"draining"} │
│         │                                                 │
│         ▼                                                 │
│  Wait 60s            native, no compute                   │
│         │                                                 │
│         ▼                                                 │
│  Heartbeat           AWS SDK integration, no Lambda        │
│    autoscaling:recordLifecycleActionHeartbeat             │
│         │                                                 │
│         ▼                                                 │
│  CheckDrained        Lambda (in VPC)                      │
│    GET /nodes/{uuid} → sandboxCount, sandboxStartingCount │
│         │                                                 │
│         ▼                                                 │
│  Choice                                                   │
│    both counts zero      → CompleteLifecycle              │
│    elapsed > 65 min      → CompleteLifecycle (give up)    │
│    otherwise             → Wait 60s                       │
│         │                                                 │
│         ▼                                                 │
│  CompleteLifecycle   AWS SDK integration, no Lambda        │
│    autoscaling:completeLifecycleAction CONTINUE           │
└───────────────────────────────────────────────────────────┘
```

### Why Step Functions rather than a scheduled poller

A scheduled Lambda (`rate(1 minute)`) that reconciles whatever sits in
`Terminating:Wait` was considered first, on the grounds that deriving everything
from ASG state makes it self-healing against missed events. That argument does
not survive contact with the hook: `default_result = CONTINUE` already bounds
every failure, so the polling loop was buying a second copy of insurance the ASG
provides for free — at the cost of ~43,000 invocations a month and the same
volume of log noise in steady state.

Step Functions also removes Lambda from most of the work: `Wait` is a native
state with no compute cost, and both autoscaling calls are AWS SDK integrations.
Lambda is left with only the two steps that must reach into the VPC.

| | Step Functions | Scheduled poller |
|---|---|---|
| Idle cost | zero executions, zero logs | ~43k invocations/month plus logs |
| Per scale-in | ~180 state transitions, about $0.0045 | — |
| Visibility | execution history shows each node's drain, loop by loop | must be reconstructed from logs |
| Missed event | instance released when the heartbeat times out | picked up on the next tick |

The missed-event row is the one real trade, and the hook's timeout is what makes
it acceptable.

### Parameters

| Parameter | Value | Rationale |
|---|---|---|
| `heartbeat_timeout` | **300s** | The heartbeat is reliable here, so the timeout only has to cover the gap between two of them. A wedged execution releases the instance in five minutes instead of an hour. |
| Wait interval | 60s | One heartbeat per loop; matches the heartbeat cadence. |
| Max drain | **65 min** | Tier `max_length_hours = 1` bounds sandbox life at an hour; five minutes of margin, then give up and let the instance go. Revisit if any tier is widened. |
| `default_result` | `CONTINUE` | Failure releases the instance rather than stalling the ASG. |
| `kill_timeout` (orchestrator job) | **15m** | Backstop for the Nomad-side stop path. By the time the hook completes, the node is already empty and the orchestrator exits immediately, so this is only load-bearing for `nomad job stop` and `nomad node drain`. |

### Network and credentials (approach M1)

| Concern | Decision |
|---|---|
| Lambda subnets | the three private subnets (`CFNPRIVATESUBNET1/2/3`) |
| Security group | a new Lambda SG; allow it to reach the server SG on **4646** (Nomad HTTP); egress through the existing NAT |
| Reaching Nomad | `http://<server private ip>:4646/v1/nodes`, servers found with `ec2:DescribeInstances` on `tag:Name=<prefix>-server`. Consul DNS is not resolvable from Lambda, so it is not used. |
| Reaching the E2B API | the public ALB, `https://api.<domain>`, over NAT. Not the api nodes' private `:50001` — that would mean maintaining a second discovery path for no gain. |
| Credentials | `nomad_acl_token` is already a Secrets Manager secret. `admin_token` has to become one first (gap 3). |
| Lambda IAM | `ec2:DescribeInstances`, `secretsmanager:GetSecretValue` on the two secret ARNs, `AWSLambdaVPCAccessExecutionRole` |
| State machine IAM | `lambda:InvokeFunction` on the function, `autoscaling:RecordLifecycleActionHeartbeat`, `autoscaling:CompleteLifecycleAction` |

## Failure modes

| Failure | Behaviour |
|---|---|
| EventBridge does not deliver the event | No execution. The instance waits in `Terminating:Wait` for 300s, then `CONTINUE` releases it. Sandboxes on it are lost — the same as today, so this is not a regression. |
| Lambda cannot reach Nomad (all three servers down) | `MarkDraining` fails and is retried by the state machine. If it keeps failing, the heartbeat stops and the hook releases the instance after 300s. Deliberate: with Nomad down the cluster is already unusable, and holding one termination open does not help. |
| Lambda cannot reach the E2B API | Same path as above. The node stays `Ready` in the API's view, so the API keeps placing sandboxes on a node that is about to die — the worst case here, and the reason `MarkDraining` retries before anything else happens. |
| Sandboxes outlive the 65-minute budget | The execution gives up and completes the action; the instance terminates with sandboxes still on it. Only reachable if a tier allows sessions longer than an hour. |
| Two instances terminate at once | Two independent executions. Nothing is shared between them. |
| Node has zero sandboxes at termination | `CheckDrained` returns zero on the first loop; the instance terminates after roughly one Wait interval. |

## Prerequisites

Both are independent fixes worth making regardless of this design.

1. **`admin_token` moves into Secrets Manager.** Terraform generates it with
   `random_password` and stores it as `${prefix}-admin-token`, the way the other
   six secrets already work; `start.sh` reads it instead of calling `openssl`.
   Without this the token rotates under the automation's feet — and it is
   already broken today, so the api job needs one redeploy to pick up the stable
   value.
2. **`kill_timeout` on the orchestrator job.** Independently useful: it makes
   `nomad job stop` and `nomad node drain` graceful, which today they are not.

## Implementation plan

| Step | Files | Verification |
|---|---|---|
| 0a | `infra-iac/terraform/main.tf`, `infra-iac/terraform/start.sh` | `admin_token` stable across two consecutive applies; `GET /nodes` returns 200 |
| 0b | `nomad/origin/orchestrator.hcl` | `NODE_ID` unchanged (M1 keeps the Nomad UUID); no change needed here |
| 1 | `nomad/origin/orchestrator.hcl` | `nomad job stop orchestrator` shows the full drain sequence in the logs: `Starting drain phase` → `graceful sandbox drain complete` |
| 2a | `infra-iac/terraform/main.tf` | lifecycle hook present on the client ASG; a termination visibly pauses in `Terminating:Wait` |
| 2b | `infra-iac/lambda/drain-warden/` plus terraform | invoke the function directly with a known instance id and confirm it resolves the node UUID and the sandbox count |
| 2c | terraform (state machine, EventBridge rule, IAM) | full rehearsal: start a sandbox with a long timeout, run `start-instance-refresh`, and watch the execution hold the instance until that sandbox ends |

The rehearsal in 2c needs `aws autoscaling start-instance-refresh`, which the
operator runs.

## Open items

- The SDK integrations
  `arn:aws:states:::aws-sdk:autoscaling:recordLifecycleActionHeartbeat` and
  `:completeLifecycleAction` are assumed to exist. They follow the standard
  pattern for the ~200 services Step Functions supports, but this has not been
  tested in this account. Fallback: move both calls into the Lambda, which
  changes nothing architecturally.
- Whether to also protect a busy node from being *chosen* for scale-in
  (`NewInstancesProtectedFromScaleIn` plus a controller that clears protection
  when a node is empty). Not needed for correctness, since draining is graceful
  whichever node is picked, and it adds a second control loop. Deferred.
- The 65-minute budget is derived from a tier value in the database. Nothing
  currently notices if that value changes. A cheap guard would be for
  `CheckDrained` to read the tier cap and fail loudly if it exceeds the budget.
